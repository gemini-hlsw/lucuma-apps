# Explore

## Running Explore Locally

```bash
# Terminal 1: continuous Scala.js compilation
sbt -J-Xmx6g '~explore_app/fastLinkJS'

# Terminal 2: install deps + start Vite dev server
pnpm install --frozen-lockfile --filter explore --prefer-offline
cd explore && pnpm exec vite
# Serves at https://local.lucuma.xyz:8080
```

## The observation subquery

`ObservationSubquery` is the single observation subquery, used by the bulk summary
query (first paint), the `observationEdit` subscription, and the create/clone
mutations. It selects only the lightweight `BasicConfiguration` for `observingMode`;
the full `ObservingMode` is hydrated separately via `ObservingModeByTypeSubquery`
(see `hydrateObservingMode` in `OdbObservationApiImpl`).

## User preferences (Hasura) migrations

The user-preferences DB is a Hasura project under `explore/hasura/user-prefs`.
**Never hand-write or hand-edit anything in there.** Every artifact in that
directory is generated by the `hasura` CLI, which is on the devshell PATH.

Rules:

- Create migrations with `hasura migrate create <name> --database-name default
  --up-sql '...' --down-sql '...'`, run from `explore/hasura/user-prefs`. Do not
  create the `migrations/default/<version>_<name>/` directory by hand. A version
  number ending in `000` is the tell that someone computed the timestamp instead
  of letting the CLI stamp `Date.now()`.
- Never modify an already-committed migration. Hasura keys applied migrations by
  version number, so an edit to a migration that has run anywhere is silently a
  no-op there while appearing correct in git. Add a new migration instead.
- Never hand-edit `explore/app/src/clue/resources/UserPreferencesDB.graphql`.
  Regenerate it by introspecting a server that has the migration applied. Editing
  it by hand makes the build pass against a schema no running server has, which is
  precisely how a missing migration turns into preferences silently reverting to
  their defaults.
- Writing the migration is only half the job. The `endpoint` in `config.yaml`
  (`user-prefs-master`) is just the authoring DB the console talks to; applying
  there reaches no deployed environment. Dev, test and production each need their
  own `hasura migrate apply --database-name default --endpoint <env>`, using the
  `nURI` values from
  `explore/common/src/main/public/environments.conf.json`. Confirm each one with
  `hasura migrate status --endpoint <env>`. Ask before touching test or
  production.
- If `migrate status` lists a version as `Not Present` in the source but present
  on the server, someone authored it through the console and never committed the
  generated files. Recover them rather than leaving the drift.
- Adding a new `TableId` also needs a row in `lucumaTableIds`; the FK on
  `lucumaTablePreferences.tableId` will otherwise reject every save, and saves are
  swallowed by `.attempt`.
